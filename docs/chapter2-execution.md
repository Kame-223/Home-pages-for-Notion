第二章　実行を支えるシステム（PC・スマホ同期）

2.0 一行定義

スマホ ≠ 常に開いて操作するもの。スマホ ＝
次の行動と今の行動を認識する装置。PCとスマホは同期し、一つの実行環境をなす。

第一章で特定した最大の欠落──「計画はできるが実行へ押し出す力がない」──に応答するのが本章である。

2.1 一日のフロー

【朝】スマホを開く

→ 朝のルーティンが表示される（一つずつ実行）

→ ルーティン内に「今日やることを決める」が含まれる

→ ルーティン完了時、「今日やること」と「今日のスケジュール」が確定

→ スケジュールが画面に表示され、予定時刻が近づくと通知

【夜】夜のルーティン

→ 翌日のスケジュールを確認

→ 未知の場所への移動時間を調べ、翌日の予定に入れる

→ 翌朝、未知の場所も「既知の移動時間を持つ予定」になっている

**朝のルーティンを終えるだけで、その日の計画が自然に立っている。**「今日やることを決める」という高コストの思考を、ルーティンの一部として埋め込む（原則②：感情に頼らない）。

**夜のルーティンは「明日を準備する」場である。**君が苦手な移動時間の見積もりを、焦っている当日ではなく冷静な前夜に前倒しすることで、不明瞭を構造的に消す。

2.2 予定の構造 ── 三種類の行動

  -----------------------------------------------------------------------------------------------
  **種類**   **例**               **時刻**             **盾の介入**            **移動**
  ---------- -------------------- -------------------- ----------------------- ------------------
  事前予定   授業・友達との約束   固定（動かせない）   移動STARTのみ           移動ブロックあり

  当日行動   課題・読書           柔軟（前後できる）   STARTロック             基本なし

  移動       寮→教室              事前予定から逆算     移動START（操作自由）   ─
  -----------------------------------------------------------------------------------------------

初版では外的予定・内的予定の二分としていたが、「移動」を独立した行動として加え、三種類に更新する。

事前予定と移動ブロック

事前予定（時刻固定）には、本体の前に移動ブロックが自動で付く。

例：3限の授業（13:30開始）

移動ブロック ... 13:20〜13:30（寮内固定値10分）

本体 ... 13:30〜15:00

→ 君が見るのは「13:20に移動START」。13:30ではなく。

-   **寮内固定値**：寮を起点とする授業移動は一律10分前にSTARTが出る（毎回考えなくていい）

-   **場所ペア登録**：その他の移動は「出発地→目的地」ごとに移動時間を事前登録しておく

-   **未知の場所**：夜のルーティンで翌日に調べて登録（当日ギリギリの判断を構造が前倒しで消す）

移動中の表示

移動ブロックのSTARTを押すと「移動中」と表示される。

-   **操作は自由**：連絡・音楽など許可。移動は作業ではないためロックをかけない。

-   **「移動中」は常に表示**：他の画面に移動しても「移動中」の表示が消えない。静かな錨として、今どの文脈にいるかを伝え続ける。

これは**盾（ロック）ではなく錨（状態の保持）**である。移動中に君を縛らないが、文脈を失わせない。

当日行動の前後移動

-   早く完了した場合：「完了」を押すと、次の当日行動が前倒しされる。次が事前予定（時刻固定）なら前倒しできないため空き時間になる。

-   長引いた場合：後続の当日行動が自動で後ろ倒しになる。次の事前予定にぶつかる前に枠タイマーの点滅で警告する。

2.3 実行の盾 ── STARTボタンと操作ロック

当日行動（内的予定）の時刻が来ると、PCとスマホ両方に同期して盾が現れる。

1.  画面にSTARTボタンが出る（PC・スマホ両方に同期）

2.  **STARTを押す以外の操作ができなくなる**（他アプリ・他画面への逃げ道を塞ぐ）

3.  STARTを押すと同期タイマーが始まる

この仕組みは「やれ」と命じない（原則③）。ただ逃げ道を塞ぐだけ。**構造がすることは、逃げ道を塞ぐことだけ。**

2.3.1 解除の摩擦設計

-   **解除には最低10分かかる**：衝動のピークはこの待ち時間に耐えられず萎える。本当に必要な用事なら10分は待てる。摩擦が「衝動」と「必要性」をふるい分ける。

-   **解除は1日でリセットされる**：翌日には盾が立ち直る。永久ロックではなく、流動性を保つ（原則①）。

-   **労力の向きの反転**：盾の維持はノーコスト。逃げる側にだけコストがかかる。

*※
母親にパスコードを預けるA方式は自己主権・流動性の観点から本線としない。緊急時の最終手段としてのみ保留。*

2.4 同期タイマーの設計

STARTを押すと起動するタイマーは、PCとスマホで完全同期し、どの画面に移動しても表示され続ける。これは「今この予定が実行中だ」という状態を静かに伝え、自己監視を促す静かな錨である。

2.4.1 二層構造

  --------------------------------------------------------------------------------------------
  **層**       **役割**                              **表示**           **主張の強さ**
  ------------ ------------------------------------- ------------------ ----------------------
  枠タイマー   予定の枠を管理（例：13:00〜15:00）    薄く、背景に沈む   弱い／静かに在るだけ

  ポモドーロ   枠の中で作業/休憩を刻む（25分/5分）   手前に表示         強い／君が従う
  --------------------------------------------------------------------------------------------

**ポモドーロを構造に組み込む理由：**「いつ休むか」を自分の判断に委ねると、休憩のつもりがYouTubeへの逃げ道になる。「自由にすると暴走する」という自己認識に基づき、休憩のタイミングを構造が刻む（原則②）。

2.4.2 終了時の挙動

-   **点滅で知らせる**：音・振動なし。視界に入れば気づくが、入れなければ集中を妨げない。刺激として強すぎる通知を避ける（原則③）。

-   **延長 or
    完了を選べる**：タイマー終了時に二択が現れる。命じない。選ぶのは君だ。

2.4.3 同期の実装方針

カウンターを各デバイスで別々に動かすとズレが生じる。以下の方針でラグを原理的にゼロにする。

① STARTを押した瞬間の「開始時刻」をサーバー（Notion）に書き込む

② 各デバイスは「現在時刻 − 開始時刻」から残り時間を自分で計算して表示

③ 完了したら完了状態をサーバーに書き込む → 両デバイスが完了状態になる

→ タイマーの実体はサーバー上の「開始時刻」という一点。同期問題が消える。

2.4.4 実行ログ

実行記録（開始・終了・実際の作業時間）を残す。ただし**自分が確認するためのものではなく、研究データとして蓄積する。**記録されること自体が評価・採点のプレッシャーにならないようにする。既存のNotion保存システム（saveFocusTotalToNotion）と接続可能。

2.5 刺激娯楽（YouTube等）の二層ゲート

刺激娯楽アプリは「禁止」ではなく「使える条件と上限」を構造化する（原則①：供給の段階的減算）。

-   **第一層／時間帯ゲート**：使用可能は12時以降。午前中は完全に閉じる。朝は予定がルーティンで確定する時間であり、刺激依存が最も危険な時間帯。午前は刺激ゼロで向き合う。

-   **第二層／使用枠と上限**：12時以降も無制限ではない。朝のルーティンで「今日YouTubeを見る時間」を予定として確保し、その枠内でのみ使用可能。上限を設ける（最大1〜3時間、漸進的に調整）。

**思想的位置づけ：**YouTubeを「当日行動」の一種として扱う。衝動で開くのではなく、計画で開く。「なんとなく開く」を構造的に消す。

2.6 アプリ環境の制限

-   **常時使えるアプリ**：生活必須のみ（Google／LINE／Google
    Maps／Claude など）

-   **刺激娯楽アプリ**：2.5の二層ゲートに従う

-   **その他**：そもそもスマホに入れるアプリ自体を制限する

-   **画面**：基本は白黒（原則③：刺激の減算）

実装課題（第二章）

**対象デバイス：**iPhone（iOS）

-   **操作ロックの実現**：iOSは一つのアプリが他アプリを完全ロックすることを禁じている。「完全なロック」ではなく「強い摩擦」での実装を検討（スクリーンタイム／集中モード／ショートカット自動化／ブロックアプリ）。

-   **比較的実装しやすい入口**：2.5の時間帯ゲート（12時前ブロック）と1日上限はスクリーンタイム標準機能で実現しやすい。ここから着手するのが現実的。

-   **タイマー同期**：絶対時刻ベース（開始時刻をNotionに書き込み、各デバイスが残り時間を自己計算）。カウンターの同期は行わない。

-   **PC側の盾**：homepageに予定時刻のSTARTボタンと、作業開始後に常駐するタイマー表示を実装する。どのタブに移動しても消えない形にする。

-   **設計フェーズでは理想構造を維持する。**現実への妥協は実装フェーズの仕事。
